# Remote repository for a gitopsify migration

gitopsify writes the repository locally and pushes it with the person's own
`git` credentials (`gitopsify generate --push`), but only to a remote that
already exists. Creating that remote, protecting it and giving the GitOps tool
access is your part: it needs organization permissions and differs per host.

Ask before creating anything, and confirm the name, owner (user, org, group or
project) and visibility. Default to **private**.

## Steps

1. Create the repository, empty (no README, no license), default branch
   `main` or whatever `output.repo.revision` says.
2. Use its URL as `--repo-url` (or `output.repo.url`) and regenerate if the
   URL changed: the generated Argo CD and Flux objects contain it.
3. Push: `gitopsify generate --push`, or `git -C gitops push -u origin main`.
4. Create a **read-only** credential for the GitOps tool, scoped to this one
   repository: a deploy key (SSH) where the host has them, otherwise a
   read-only token from a service account.
5. Protect the default branch (reviews, no force pushes) once the first push
   is in.
6. Pass the credential to `gitopsify bootstrap` (`--ssh-key` and
   `--known-hosts`, or `--git-token`/`--git-username`). Keep key files out of
   the repository and delete them locally when bootstrap is done.

SSH deploy keys, generated per environment:

```sh
ssh-keygen -t ed25519 -N '' -C gitopsify-uat -f ./deploy-uat
ssh-keyscan <git-host> > known_hosts      # Flux always needs it; Argo CD knows the big hosts
```

Argo CD ships host keys for GitHub, GitLab, Bitbucket and Azure DevOps;
gitopsify adds `--known-hosts` entries for anything else. Flux needs
`--known-hosts` for every SSH URL. Flux doesn't accept `git@host:path` URLs;
gitopsify converts them to `ssh://git@host/path` for you.

## GitHub

```sh
gh repo create acme/platform-gitops --private --description "GitOps repository generated by gitopsify"
gitopsify generate --repo-url https://github.com/acme/platform-gitops.git --push
gh repo deploy-key add deploy-uat.pub -R acme/platform-gitops --title gitopsify-uat   # read-only by default
gitopsify bootstrap --env uat --ssh-key deploy-uat --known-hosts known_hosts
```

With an SSH key, the repository URL Argo CD and Flux use must be the SSH one
(`git@github.com:acme/platform-gitops.git`): generate with that URL. For
HTTPS instead, create a fine-grained personal access token (or one for a
machine user) with **Contents: Read-only** on this repository only, and pass
`--git-token`. Organizations that use GitHub Apps can register the app in Argo
CD or Flux instead; that is configured in the tool, after bootstrap.

## GitLab

```sh
glab repo create acme/platform-gitops --private
gitopsify generate --repo-url git@gitlab.com:acme/platform-gitops.git --push
glab api --method POST "projects/acme%2Fplatform-gitops/deploy_keys" \
  -f title=gitopsify-uat -f key="$(cat deploy-uat.pub)" -f can_push=false
```

For HTTPS, a **deploy token** with `read_repository`: its username goes in
`--git-username`, the token in `--git-token`.

```sh
glab api --method POST "projects/acme%2Fplatform-gitops/deploy_tokens" -f name=gitopsify-uat -f 'scopes[]=read_repository'
```

Self-managed GitLab works the same with `GITLAB_HOST` set.

## Azure DevOps

```sh
az devops configure --defaults organization=https://dev.azure.com/acme project=Platform
az repos create --name platform-gitops --query '{https:remoteUrl, ssh:sshUrl}'
```

- Use the URL without a user name: `https://dev.azure.com/acme/Platform/_git/platform-gitops`.
- Push with the person's Git Credential Manager login, or with a PAT for one
  push: `git -c http.extraHeader="Authorization: Basic $(printf ':%s' "$PAT" | base64 | tr -d '\n')" -C gitops push -u origin main`.
- Azure DevOps has no per-repository deploy keys; SSH keys belong to a user.
  Prefer HTTPS with a PAT of a dedicated service account, scope **Code
  (Read)**, created in User settings → Personal access tokens. Pass it with
  `--git-token "$PAT" --git-username git` (any non-empty user name works).
- For SSH, use an RSA key (`ssh-keygen -t rsa-sha2-512 -b 4096` or `-t rsa -b
  4096`): Azure DevOps has long accepted only RSA keys. Host keys:
  `ssh-keyscan -t rsa ssh.dev.azure.com > known_hosts`. The SSH URL looks like
  `git@ssh.dev.azure.com:v3/acme/Platform/platform-gitops`.
- PATs expire: note the expiry date in the hand-over, or use Entra workload
  identity if their Argo CD or Flux version supports it for Azure DevOps.
- Set a branch policy on `main` in Project settings → Repositories → Policies.

## Bitbucket Cloud

```sh
curl -fsS -u "$BB_EMAIL:$BB_API_TOKEN" -H 'Content-Type: application/json' \
  -X POST "https://api.bitbucket.org/2.0/repositories/acme/platform-gitops" \
  -d '{"scm": "git", "is_private": true}'
curl -fsS -u "$BB_EMAIL:$BB_API_TOKEN" -H 'Content-Type: application/json' \
  -X POST "https://api.bitbucket.org/2.0/repositories/acme/platform-gitops/deploy-keys" \
  -d "{\"label\": \"gitopsify-uat\", \"key\": \"$(cat deploy-uat.pub)\"}"
```

For HTTPS, a repository access token with read access: user name
`x-token-auth`, password the token. Bitbucket Data Center has repository
access keys (SSH) and HTTP access tokens with the same roles.

## Gitea and Forgejo

```sh
tea repos create --name platform-gitops --private          # or POST /api/v1/user/repos
curl -fsS -H "Authorization: token $GITEA_TOKEN" -H 'Content-Type: application/json' \
  -X POST "https://git.acme.io/api/v1/repos/acme/platform-gitops/keys" \
  -d "{\"title\": \"gitopsify-uat\", \"key\": \"$(cat deploy-uat.pub)\", \"read_only\": true}"
ssh-keyscan git.acme.io > known_hosts
```

## AWS CodeCommit

```sh
aws codecommit create-repository --repository-name platform-gitops
aws iam create-service-specific-credential --user-name gitops-reader --service-name codecommit.amazonaws.com
```

Use the HTTPS URL (`https://git-codecommit.<region>.amazonaws.com/v1/repos/platform-gitops`)
and the generated user name and password with `--git-username`/`--git-token`.
Give `gitops-reader` only `codecommit:GitPull` on this repository.

## Self-hosted servers with a private CA

gitopsify's bootstrap doesn't install CAs for Git servers. After bootstrap:

- Argo CD: add the CA to the `argocd-tls-certs-cm` ConfigMap under the
  server's host name.
- Flux: add `ca.crt` to the Git credentials Secret (`flux-system` in the
  Flux namespace by default).

## An existing repository

To put the output into a repository that already holds other things, generate
into its working copy with `--repo-path <dir>` (the path inside the
repository) and `-o <clone>/<dir>`, then commit and push yourself, ideally
through a pull request.

## When a push or sync fails

| Symptom | Likely cause |
|---|---|
| `remote: Repository not found` / 403 on push | Wrong owner or name, or the person's credentials lack write access |
| `already has remote origin X, not Y` | The output directory was pushed elsewhere before; fix `--repo-url` or the remote |
| Argo CD `authentication required` | No or wrong credential; check the `gitopsify-repo` Secret in the Argo CD namespace and that the URL type (SSH/HTTPS) matches the credential |
| Flux `unable to clone ... knownhosts: key is unknown` | `--known-hosts` missing or for another host; rerun `ssh-keyscan` |
| Flux `ssh: handshake failed` with Azure DevOps | A non-RSA key |
