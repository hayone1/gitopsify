# Troubleshooting and questions

Start with `gitopsify doctor`: it checks your tools, configuration, cluster
access and permissions, and Git remotes in one go, and explains each problem.

## Connecting

See [Cluster access](authentication.md#when-it-doesnt-connect): every
connection error comes with what to do.

## Scanning and generating

**An object I expected is missing.** Run `gitopsify scan --show-excluded` and
look it up: the rule and the reason are there. `gitopsify rules` describes
each rule; switch one off with `--disable-rule <name>`, or include specific
objects with a `scope.rules` entry (`action: include`).

**Something I didn't expect is included.** Exclude it with `scope.rules` or
`--exclude-kind`, or narrow the scope with `-n`, `-r` or `-l`.

**A kind is missing and the warnings say "not allowed to list".** Your
credentials can't read that kind, so nothing of it was migrated. Use an
account that can (see [least privilege](authentication.md#least-privilege)).

**"listing X failed, so none are migrated".** A custom API failed repeatedly,
typically a CRD whose conversion webhook is down. Fix it in the source, or
accept that kind is missing.

**A Helm release is vendored or turned into manifests.** Its repository wasn't
found. Set `helm.repositories.<chart>`; see [Helm](helm.md).

**`is not empty and was not generated by gitopsify`.** gitopsify won't write
into a directory it didn't create. Pick another `-o`, or `--force`.

**`generate --push` is rejected.** If the remote branch has commits the
output directory doesn't, generate into a fresh directory (gitopsify checks the
remote branch out first and builds on it) or pull first.

## Checking the target

**`api` errors: a version or kind isn't served.** The target runs another
Kubernetes version, or lacks an operator. Install the operator, migrate it
too, or exclude the objects.

**StorageClass or IngressClass doesn't exist.** Map it:
`--storage-class standard=gp3`, or a transform per environment.

**`diff` shows changes on a cluster that already runs the apps.** Usually
Helm drift or fields another tool owns; see [Takeover](takeover.md#2-make-the-diff-clean).

## After bootstrap

`gitopsify status --env <env>` shows each app's first error. The common ones:

| Symptom | Cause |
|---|---|
| `no matches for kind ...` | A CRD isn't installed yet; it syncs in an earlier wave, or must be installed |
| `failed calling webhook` | The operator isn't ready yet; apps retry, or move the operator to an earlier wave |
| Pods in `CreateContainerConfigError` or `ImagePullBackOff` | A Secret or pull secret listed in the report wasn't created |
| `authentication required` | The repository credentials (`--git-token`, `--ssh-key`) are missing or wrong |
| `knownhosts: key is unknown` (Flux) | `--known-hosts` is missing or for another host |
| An app stays `OutOfSync` | A controller rewrites a field that Git sets; drop the field with a `remove` transform |

## Questions

**Does gitopsify change my source cluster?** No. It only reads it. Only
`adopt`, `bootstrap` and `migrate` change a cluster, and only the environment
you name.

**Does it copy data?** No. Persistent volume data and images stay where they
are. Use Velero or `crane transfer-pvc` for data and your registry's
replication for images, before you switch traffic.

**Can it convert between Argo CD and Flux?** No. Objects one of them already
manages are left out by default, because their source is already in Git.
`--include-managed` migrates them as plain objects.

**Can I run it in CI?** Yes: `--no-input`, credentials from
`GITOPSIFY_TOKEN`/`GITOPSIFY_TARGET_TOKEN` or a kubeconfig, and `diff
--exit-code` or `status --wait` as gates.

**Can I edit the generated files?** Prefer changing `gitopsify.yaml` and
regenerating, so the change survives the next run. Files you add yourself are
kept when you regenerate.

**Which Kubernetes versions?** Whatever the API server serves: gitopsify asks
it. The pinned Argo CD and Flux versions decide what the target needs; `check`
verifies API versions against the target.
